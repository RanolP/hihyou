# Phabricator Differential and Mozilla's review workflow

Research for hihyou, a "platform-agnostic diff-set viewer". The problem it answers, in the user's words: "just seeing sequence of diffs without any intention makes user 피로. so reviewing on github makes us 피로. seeing pr on vs code is a way better. but not enough;". This note looks at Phabricator's Differential, and at how Mozilla uses it, for functionality only, not look: what each feature does to reviewer fatigue and to carrying the author's intention.

Convention: plain sentences with a link are **sourced fact**. **Observed** marks what I saw myself on `phabricator.services.mozilla.com` on 2026-09-29. **Inference** marks my own reasoning.

## 1. The unit of review: revision, diff, commit, stack

A **revision** (`D123`) is the unit people review: "An author prepares a change to a codebase, then sends it for review", reviewers "inspect the change and either discuss it, approve it, or request changes", and the author "may update the change" ([Differential User Guide](https://secure.phabricator.com/book/phabricator/article/differential/)). A **diff** is one uploaded patch. A revision holds a sequence of diffs, one per round. Phabricator "works off of arbitrary patches (called diffs internally) that can be turned into stacks of patches using parent/child relationships", while a GitHub PR is "based off of the commits that are different from some base commit" ([Firefox: Phabricator vs GitHub](https://firefox-source-docs.mozilla.org/contributing/phabricator_vs_github.html)).

A **commit** maps to exactly one revision by design. The house rule is "One idea is one commit", because "when one idea is many commits, everything you do is more complicated because you need to figure out which commits represent an idea" ([Recommendations on Revision Control](https://secure.phabricator.com/book/phabflavor/article/recommendations_on_revision_control/)). The same rationale covers reviewer load: "ten 200-line changes each doing one thing are often far easier to understand than one 2,000 line change doing ten things", and a commit message should "explain _why_ you are making the change" ([Writing Reviewable Code](https://secure.phabricator.com/book/phabflavor/article/writing_reviewable_code/)). Authors rewrite history. Phabricator "assumes you will be rewriting history" and keeps identity through a `Differential Revision:` trailer in the commit message ([Firefox: Phabricator vs GitHub](https://firefox-source-docs.mozilla.org/contributing/phabricator_vs_github.html)). Epriestley recommends squash/rebase workflows. When several commits map to one revision, the displayed change is picked arbitrarily ([T4453](https://secure.phabricator.com/T4453)).

A **stack** is a chain of revisions linked by parent/child edges. Mozilla's `moz-phab` turns local commits into such a series ("support for commit series ... stacks of dependent changesets", [Mozilla Phabricator User Guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)), and `moz-phab reorg` rewrites the parent/child edges after a local reorder ([Stack quick reference](https://firefox-source-docs.mozilla.org/contributing/stack_quickref.html)). Reviewers see the stack in the "Revision Contents" section, where "the top of the stack (most recent change) is first in the list" ([Stack quick reference](https://firefox-source-docs.mozilla.org/contributing/stack_quickref.html)). The edges are "internal relationships only tracked through the web interface" ([Firefox: Phabricator vs GitHub](https://firefox-source-docs.mozilla.org/contributing/phabricator_vs_github.html)). Each revision in a stack is reviewed and accepted on its own. Lando lands a stack: open "the child-most commit of the stack you want to land", click "View Stack in Lando", and it lands the ancestors too, possibly as "partial landings of a subset of the stack" ([Lando User Guide](https://moz-conduit.readthedocs.io/en/latest/lando-user.html)).

Observed: [D250000](https://phabricator.services.mozilla.com/D250000) ("Bug 1820252 - Add FindBar tests r=#translations-reviewers") shows the tabs Files, History, Commits and Stack. The Stack tab lists 23 related revisions (D249967 through D250351) and the History tab lists 19 diffs uploaded over 3 days. Of the 40 newest revisions in the public listing, 6 showed a Stack tab.

How it differs from a GitHub PR. Gregory Szorc (a former Mozilla engineer) argues that GitHub's "default is to show the _merge diff_", and that per-commit feedback on GitHub "gets lumped together into one massive pile of feedback for the pull request as a whole", whereas "review comments and discussion need to be bucketed by commit". Phabricator buckets them per revision, which is to say per commit ([Problems with Pull Requests](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/)). A stack can land part by part, while a PR is one unit of merging ([same](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/); [Lando User Guide](https://moz-conduit.readthedocs.io/en/latest/lando-user.html)). A diff has no fixed base branch, so "we can freely reorder two differentials" ([MaskRay on LLVM's switch](https://maskray.me/blog/2023-09-09-reflections-on-llvm-switch-to-github-pull-requests)). GitHub has closed part of this gap: Stacked PRs went to private preview in April 2026 ([The Register](https://www.theregister.com/2026/04/14/github_stacked_prs/)) and to public preview on 2026-07-30, with a "stack map" at the top of each PR and each PR showing "only the differences for that specific layer" ([GitHub changelog](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/)).

## 2. Intention carriers: title, summary, test plan, bug, reviewers

A revision carries a title, a **Summary**, a **Test Plan**, reviewers, subscribers, and at Mozilla a Bugzilla bug ID. The test plan is "a repeatable list of steps which document what you have done to verify the behavior of a change", and it is required by default, though "this can be disabled or made optional in the config" ([Test Plans](https://secure.phabricator.com/book/phabricator/article/differential_test_plans/)). These fields are derived from the commit message and render above the diff, on the revision page. The revision page shows title, summary, test plan and reviewers first, then the timeline, then "Revision Contents" with the changeset (observed on D250000 and [D329608](https://phabricator.services.mozilla.com/D329608)).

Mozilla requires a bug: "A bug number must be entered when a patch is submitted", and the revision is mirrored as a stub attachment on the bug ([Mozilla Phabricator User Guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)). The commit title follows the format "Bug 123456 - Change this thing to work better by doing something. r=reviewers", with extra rationale after a blank line only "if reasoning isn't obvious" ([How to submit a patch](https://firefox-source-docs.mozilla.org/contributing/how_to_submit_a_patch.html)). So at Mozilla most of the *why* lives in Bugzilla, one click away from the diff.

Observed, sample of the 40 newest revisions on 2026-09-29, reading the commit-message block that Phabricator renders in the Commits table (present on 31 of 40): the **Test Plan was empty on 31 of 31**, and the **Summary was empty on 17 of 31**, meaning title only. Example: D329608 "Bug 2071241 - Remove panel-list's workaround for bug 2066409" has an empty Summary and an empty Test Plan. Inference: at Mozilla the intention carrier that actually works is the one-line title plus the linked bug. The structured Test Plan field exists but goes unused.

## 3. Updates between rounds: history, diff-of-diffs, carried-forward comments

**Diff-of-diffs.** The History tab lists every uploaded diff plus a "Base" row, with two radio columns (left `vs`, right `id`) and a "Show Diff" button. The URL form is `D250000?vs=1037582&id=1040160` (observed: 19 radio pairs on D250000, and the compare URL renders Diff 1037582 against Diff 1040160). Any two rounds can be compared, not only the last two: "The user interface allows for comparisons between any two revisions" ([MaskRay](https://maskray.me/blog/2023-09-09-reflections-on-llvm-switch-to-github-pull-requests)). Light green and light red backgrounds mark lines that "are part of the diff but they were not added or removed by the author", that is, rebase noise ([Differential FAQ](https://secure.phabricator.com/book/phabricator/article/differential_faq/)). In an interdiff, a file that did not change and whose inlines are all collapsed "is now hidden by default" ([Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)).

**Ghost inlines.** When a revision is updated, Differential ports inline comments forward: "Ported comments have a pale, ghostly appearance and include a button which allows you to jump back to the original context". The porting is deliberately aggressive: "We can not know if the change addressed the inline or not ... we won't drop important inlines just because the structure of the code has changed". A preference ("Show Older Inlines") turns it off ([Inline Comments](https://secure.phabricator.com/book/phabricator/article/differential_inlines/)). Epriestley's reasoning: "As a reviewer, I think bringing 'Done' comments forward is quite important: it makes it a lot easier for me to verify that they're really done", and "It's much better to bring them forward (even if they aren't on the right lines) than to drop them" ([T7447](https://secure.phabricator.com/T7447)).

**Done.** Each inline has a Done checkbox. The state is published and exposed through the API as `isDone` ([Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)). Observed on D250000: the reviewer's inline about `SwapDocShells` was marked Done. Mozilla's UI string table also includes "Mark or unmark selected inline comment as done.", "Hide Older Inlines", "Hide Collapsed Inlines" and "List Inline Comments" (observed in page source).

**Accept carries forward.** With `differential.sticky-accept`, an accepted revision stays accepted after an update, and the author can "request review" again for significant changes ([FAQ](https://secure.phabricator.com/book/phabricator/article/differential_faq/)). Mozilla's docs put it this way: "no need to manually 'carry forward' reviews ... the changes will show as accepted" ([Bugzilla Equivalents](https://wiki.mozilla.org/Phabricator/Bugzilla_Equivalents)), and minor fixes after "Accept Revision" need no re-review ([How to submit a patch](https://firefox-source-docs.mozilla.org/contributing/how_to_submit_a_patch.html)).

## 4. Reading aids

- **Paths panel (file tree)**: always on since April 2020, toggled with `f` ([T13516](https://secure.phabricator.com/T13516), [Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)).
- **Keyboard navigation**: the observed string table includes jump to next or previous change, file, and inline comment; jump to the table of contents; hide or show the current changeset; open the file in an external editor (`\`, [Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)).
- **Per-file view state**: "Changeset view state ('Highlight As...', 'Hidden', etc.) is now persistent" ([Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)). A reviewer can hide a file they are done with, and it stays hidden.
- **Moved and copied code**: a yellow "copied/moved" gutter drawn by application-level detection (`detectCopiedCode`). Epriestley called linking each marker to its source block "tricky in the general case" ([T13161](https://secure.phabricator.com/T13161)).
- **Whitespace**: the older whitespace modes were replaced by normalized diffs that show indent-depth changes with `<<` and `>>` markers instead of hiding them ([T13161](https://secure.phabricator.com/T13161)).
- **Context expansion**: "Show 20 lines" and "Show All Context" links ([D15009](https://secure.phabricator.com/D15009), [T11737](https://secure.phabricator.com/T11737)). Expansion needs the uploaded diff to carry full context, which is why LLVM told authors to upload with `-U999999` ([LLVM Phabricator docs](https://releases.llvm.org/14.0.0/docs/Phabricator.html)).
- **Generated files**: `@generated` in a file, or `differential.generated-paths`, folds the changeset at display time ([T8527](https://secure.phabricator.com/T8527), [T6378](https://secure.phabricator.com/T6378)).
- **Large files**: the observed string table has "Load Changes", so big changesets render on demand. The upstream "Large Changes" guide now reads "This atom no longer exists" ([link](https://secure.phabricator.com/book/phabricator/article/differential_large_changes/)).
- **Syntax highlighting**: through Pygments, plus a per-file "Highlight As..." override ([FAQ](https://secure.phabricator.com/book/phabricator/article/differential_faq/)).
- **Suggest Edit**: the observed string table has "Suggest Edit", and T13161 gives suggestions higher-contrast colors ([T13161](https://secure.phabricator.com/T13161)).
- **CI in the timeline**: Harbormaster lint and unit results post on each diff. Observed on D250000: the eslint failures on Diff 1039905 were fixed in a later diff. Revisions start as drafts that "don't notify reviewers until builds pass" ([Changelog 2020.16](https://secure.phabricator.com/w/changelog/2020.16/)).
- "Show older changes" (timeline collapse) and file ordering: not verified (see Unverified).

## 5. Review actions and states

- **Accept Revision** and **Request Changes** ("Needs Revision"). With normal reviewers, "acceptance from any reviewer removes the review from that user's queue (i.e. Only a single reviewer must accept)" ([Bugzilla Equivalents](https://wiki.mozilla.org/Phabricator/Bugzilla_Equivalents)).
- **Blocking reviewer**: requires review "from that user or an explicit removal". It is Mozilla's analogue of `review?`, and `moz-phab` can make every reviewer blocking with `submit.always_blocking` ([Bugzilla Equivalents](https://wiki.mozilla.org/Phabricator/Bugzilla_Equivalents)). Group reviewers such as `#gfx-reviewers` and `#translations-reviewers` appear in titles as `r?#group` (observed on D329596 and D250000). Lando warns when "the revision has not been accepted by a blocking reviewer" ([Lando User Guide](https://moz-conduit.readthedocs.io/en/latest/lando-user.html)).
- **Plan Changes** (author): "Removes revisions from reviewers' queues ... until a new diff is uploaded". **Request Review** puts it back ([Mozilla Phabricator User Guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)).
- **Resign as Reviewer**: "you are not able to or do not wish to review this change" ([same](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)).
- **Commandeer**: take over authorship; "the original author will no longer be able to post updated diffs" ([same](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)).
- **Dashboard buckets**: "Action Required" versus "Waiting on Others" ([Differential User Guide](https://secure.phabricator.com/book/phabricator/article/differential/)).
- **Herald** "can perform actions, such as sending notifications, based on object changes" ([Mozilla Phabricator User Guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)). MaskRay credits Herald's "fairly complex subscription rules" against GitHub's all-or-nothing watching ([MaskRay](https://maskray.me/blog/2023-09-09-reflections-on-llvm-switch-to-github-pull-requests)).
- There is no feedback-versus-review distinction and no `needinfo`. Mozilla uses comments and @-mentions instead ([Bugzilla Equivalents](https://wiki.mozilla.org/Phabricator/Bugzilla_Equivalents)).

What each state tells a reviewer (inference): the queue state answers *whether* to look now. Plan Changes is the only author-side signal that says "don't look yet". Nothing in these states says *what* to look at within a revision; sticky-accept even hides post-accept changes unless the author re-requests review.

## 6. What Mozilla, and people who used Phabricator, say

**Why Mozilla adopted it (2017-2018).** Differential "addresses several of the deficiencies in Review Board and is better suited to the Firefox engineering process". It replaced MozReview and Splinter, with a stated policy of "we don't plan to support multiple tools" ([MozillaWiki: Phabricator](https://wiki.mozilla.org/Phabricator)). Phabricator and Lando launched as the primary review tool for mozilla-central ([dev-platform announcement](https://groups.google.com/g/mozilla.dev.platform/c/JKbDxHSaVfM/m/GuoQt4TlAQAJ)).

**What is good about it.**
- Commit-sized review units with feedback bucketed per unit, and partial integration of a stack ([Szorc](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/)).
- Any-two-diff comparison, free reordering of a stack, Herald, and inline comments that survive history rewrites better than GitHub's comments do after a force push ([MaskRay](https://maskray.me/blog/2023-09-09-reflections-on-llvm-switch-to-github-pull-requests)).
- A former Facebook engineer's line, quoted when GitHub announced stacks: "people who have worked with Phabricator using a 'stacked diff' workflow generally love it and seek it wherever they next go" ([The Register](https://www.theregister.com/2026/04/14/github_stacked_prs/)).

**What is bad about it.**
- `arc` squashes by default, so Mozilla had to build `moz-phab` to submit stacks. Szorc says of stacks: "There is no primary UI or APIs for _stacks_" ([Szorc](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/)).
- Stack submission was slow: one report says `moz-phab` took 20 minutes where `arc` took under 2, because it calls `arc` once per commit ([bug 1498144](https://bugzilla.mozilla.org/show_bug.cgi?id=1498144)).
- Anonymous Hacker News commenters (not verified as Mozilla staff) found arcanist "like hitting the 'I'm feeling lucky' button" ([HN](https://news.ycombinator.com/item?id=21119100)).
- Upstream maintenance ended: Phacility went into "bare minimum maintenance mode in 2021", and the community fork Phorge released on 2022-09-07 ([Wikipedia](https://en.wikipedia.org/wiki/Phabricator)).
- Epriestley refused to hide lines a child diff shares with its parent. The author must choose the base explicitly ([T11251](https://secure.phabricator.com/T11251)).

**What happened (migration status).** Firefox's version control moved from Mercurial to git, and GitHub became the canonical home in May 2025 ([heise](https://www.heise.de/en/news/Mozilla-uses-Microsoft-GitHub-as-the-official-home-for-Firefox-source-code-10384645.html), [DevClass](https://devclass.com/2025/05/14/mozilla-quietly-makes-microsofts-github-the-authoritative-home-for-firefox-code/)). Review did **not** move: "Mozilla will not be using GitHub pull requests for code submissions" ([DevClass](https://devclass.com/2025/05/14/mozilla-quietly-makes-microsofts-github-the-authoritative-home-for-firefox-code/)), and today's docs say "reviewing code happens on Phabricator and landing code happens with an integration from Lando" ([Firefox: Phabricator vs GitHub](https://firefox-source-docs.mozilla.org/contributing/phabricator_vs_github.html)). On 2026-09-29 the public instance was live and taking new revisions around D329600 (observed).

## 8. Synthesis for hihyou

**Ideas that address "a sequence of diffs without intention"**
- **One idea = one revision, with a title and a why.** A stack turns a long diff into a sequence of named, individually accepted ideas. This is the strongest idea: the intention is attached to a *unit* instead of to the whole branch. (Fact: [rev control](https://secure.phabricator.com/book/phabflavor/article/recommendations_on_revision_control/), [Szorc](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/). Rating: yes.)
- **Ghost inlines plus Done, carried forward.** The reviewer's own intention ("this needs fixing") survives into the next round and can be checked off against new code. (Fact: [T7447](https://secure.phabricator.com/T7447). Rating: yes, for the reviewer side.)
- **Any-two-diff compare, with rebase noise tinted.** It answers "what did the author change *in response to me*" without re-reading everything. (Fact: [FAQ](https://secure.phabricator.com/book/phabricator/article/differential_faq/), observed. Rating: partly. It shows *what* changed between rounds, but the round itself carries no required "why".)
- **Plan Changes, drafts until CI passes.** These keep half-done work out of the reviewer's queue. They reduce fatigue but carry no intention. (Fact: [Mozilla guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html), [2020.16](https://secure.phabricator.com/w/changelog/2020.16/). Rating: partly.)

**Ideas that only look like they carry intention**
- **Test Plan field.** Mozilla's sample showed it empty on 31 of 31 revisions (observed). A required free-text field is easy to bypass: configurable, and filled by commit-message templates. Inference: a structured intent field without a consumer decays into boilerplate.
- **Stack tab.** It is an ordered list of titles and states. It does not say why the stack is split this way, or what each layer assumes of the one below. Szorc: "There is no primary UI or APIs for _stacks_" ([source](https://gregoryszorc.com/blog/2020/01/07/problems-with-pull-requests-and-how-to-fix-them/)). Inference: order is shown, but the narrative is not.
- **Bug linkage.** The why is outsourced to Bugzilla, one click away, and is never shown next to the hunks it explains ([Mozilla guide](https://moz-conduit.readthedocs.io/en/latest/phabricator-user.html)).
- **Moved-code gutter, generated folding, whitespace normalization.** These cut noise (fatigue), not intention ([T13161](https://secure.phabricator.com/T13161), [T8527](https://secure.phabricator.com/T8527)).
- **Sticky accept.** It reduces round-trips, but it also means a reviewer may never see a post-accept change ([FAQ](https://secure.phabricator.com/book/phabricator/article/differential_faq/)).

**Gaps that remain even in Phabricator (inference, where hihyou could go further)**
1. Intent granularity stops at the revision. Nothing links a summary sentence to the hunks that implement it, and inside a revision the reviewer still reads files in tool order, not in the author's explanatory order.
2. A round has no intent. The compare view shows Diff N against Diff M, but nothing requires the author to say "this round addresses comments X and Y, and also rebased". Ghost inlines are matched by line heuristics, not by the author declaring what answered what ([T7447](https://secure.phabricator.com/T7447) admits porting "is impossible" in general).
3. No stack-level compare. You can diff two rounds of *one* revision, but not "stack v1 against stack v2" when layers are reordered, split or merged. `moz-phab reorg` only rewrites the edges.
4. The base must be explicit. Epriestley refused to derive a child's view from its parent ([T11251](https://secure.phabricator.com/T11251)). A diff-set viewer that owns `{base, head}` per unit could compute layer views itself, independent of any server.
5. Platform lock-in. All of this lives in one server app, now unmaintained upstream ([Wikipedia](https://en.wikipedia.org/wiki/Phabricator)), and GitHub is only now copying stacks ([changelog](https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/)). A client-side viewer that takes a commit, range or PR and renders "ideas + rounds + carried comments" would give the Phabricator model to any host.
6. Fatigue signals are per-file ("Hidden", "Viewed"), not per-idea. There is no "I have understood intention 2 of 4".

# Why Gerrit review felt good

Companion to `docs/research/gerrit.md`, which covers what Gerrit *does*: the change / patch set / Change-Id model, what carries across a rebase and keyed on what, and where that carry breaks. This note asks a different question: why people who used Gerrit describe reviewing there as a better *experience* than reviewing on GitHub, and what they disliked. It is the Gerrit counterpart of `phabricator-experience.md` and serves the same problem statement, in the user's words: "just seeing sequence of diffs without any intention makes user 피로 (fatigue). reviewing on github makes us 피로. seeing pr on vs code is a way better. but not enough."

Convention: a quoted sentence with a link is **evidence** (a first-hand account). **Inference** marks my own reasoning. Each reason says whether it comes from the **tool**, the **culture**, or **both**, and what GitHub does differently. Features are named only as the mechanism behind a feeling; their specs and carry rules live in `gerrit.md`.

A caveat on the evidence: many of the warmest accounts come from people who also used Google's internal Critique, which Gerrit's newer UI resembles ("Gerrit looks almost completely like Critique ... I really enjoy the user interface and whole flow of Gerrit", throwaway3699, [HN](https://news.ycombinator.com/item?id=26847429)); dietrichepp answers a fan with "Probably because you got used to Critique at Google ;)" ([HN](https://news.ycombinator.com/item?id=24919815)). The praise also skews toward people who use Gerrit daily; the dislikes skew toward newcomers and occasional contributors. That split is itself a finding (see Dislikes).

## The one-line summary

The shortest statement of Gerrit's appeal is q3k's: "a tool that looks terrible if you've never seen it before, but after learning its core concepts you will never want to use any other code review system" ([HN](https://news.ycombinator.com/item?id=27279286)). Matt Hall names the design choice behind it: "GitHub is geared to making it easy to contribute. Gerrit is geared to making it easy to make sure your code is high quality" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). Like Phabricator, nearly every reason below spends the author's effort to save the reviewer's attention; unlike Phabricator, Gerrit also spends the newcomer's effort, and that is what drove projects away.

## Reasons

### 1. Round two shows only what changed since round one

**Experience.** Coming back to a change, the reviewer reads the delta since they last looked, not the whole change again. q3k: "Easy diffing between states of the CR (patch sets), so you can see what changes since the last round of comments, even if it spanned multiple updates. This is the feature I miss the most from other code review systems" ([HN](https://news.ycombinator.com/item?id=24919786)). Matt Hall: "For each commit in the chain you can select between which version - called a patchset - you want to review. You can even select which versions you diff between meaning if the code was good and you just wanted to make sure your comments were addressed you can see what changes in the last push" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). bqmjjx0kac: "Gerrit is significantly nicer to use. It keeps track of each patch set you upload and lets you diff between them" ([HN](https://news.ycombinator.com/item?id=36608254)). The history is also a safety net for the author: "Old patch sets are still available should you wish to roll back/reference either a particular commit, or a whole chain of commits" (depressedpanda, [HN](https://news.ycombinator.com/item?id=24929577)); js2: "It lets you more easily see how development evolves in response to feedback" ([HN](https://news.ycombinator.com/item?id=24919830)).

**Mechanism.** Every upload with the same `Change-Id` becomes an immutable, numbered patch set; any two (or base) can be compared; when the two patch sets have different parents, edits explained by the rebase are tinted and rebase-only files drop out of the list (`gerrit.md` §1, §2.2). lima lists it as "Show diffs between different versions of a change, even across rebases, with inline comments" ([HN](https://news.ycombinator.com/item?id=26847429)). The Change-Id is what makes amend-and-repush safe for the reviewer: "Unlike GitHub this isn't a bad experience for the reviewer, quite the opposite!" (Matt Hall).

**Tool or culture: tool.**

**What GitHub does instead.** Force-push replaces the branch. TheDong: "The fact that it still doesn't have any idea of patchsets and diffs between them is cripplingly bad (i.e. you force push a new version of your change, there's no easy way to review the diff between the old and new version of your change)" ([HN](https://news.ycombinator.com/item?id=36608305)). bqmjjx0kac: "GitHub seems to just... forget about everything but the two most recent uploads." Matt Hall found GitHub's "See changes" link after a force push "very hit and miss, often seeing 404 style pages", with "no easy way to see the history - i.e. a list of force pushes"; tylerhou: "sometimes I get the message that the old commit can't be found" ([HN](https://news.ycombinator.com/item?id=36608263)). The alternative, fixup commits, is "pretty bad for your repository's health" (Matt Hall). I found no first-hand account praising the rebase tint by name; users praise the compare, and the tint is the part that keeps it readable after a rebase.

### 2. One commit is one review, so changes arrive small

**Experience.** The reviewer receives one atomic idea at a time. lima: "It's very annoying to stack GitHub PRs, so the default is to create large PRs instead. This is sad, because smaller units of review result in better code! Gerrit solves this" ([HN](https://news.ycombinator.com/item?id=26847429)). dietrichepp, from the reviewer's chair on GitHub: "When I review PRs on services like GitHub I *very often* think, 'This should be several different reviews'" ([HN](https://news.ycombinator.com/item?id=24919815)). Compass, even while leaving Gerrit, named this as the biggest loss: "Gerrit required all changes for a code review to be squashed into a single commit, which results in a succinct, clean git history and inherently encourages trunk-based development because of the ease of breaking up work into separate, stacked, dependent code reviews" (Nathaniel Morihara, [Compass](https://medium.com/compass-true-north/from-gerrit-to-github-cebc463ec01b)).

**Mechanism.** A change is exactly one commit (`gerrit.md` §1); there is no "PR with 14 commits". Matt Hall: "Gerrit strongly encourages - both through documentation and the UI - that you should edit your commit. This encourages you to keep your history clean and to make atomic commits. Previously when I have worked with GitHub I've had no incentive to make my commits make sense as atomic units - I've known the feature branch will be squashed and merged so why make the effort?" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). mbbx6spp: "Github's PRs do not force you to think about atomic/related changes as one commit. Gerrit's reviews ... do force developers to think about this much more consciously" ([gist](https://gist.github.com/mbbx6spp/70fd2d6bf113b87c2719)). zzzeek: "You always have a feature packaged up as a single, clean commit, so that even with 'git show', you can see the change ... all at once" ([techspot.zzzeek.org](https://techspot.zzzeek.org/2016/04/21/gerrit-is-awesome/)).

**Tool or culture: both.** The tool refuses the multi-commit unit; Qt, Go and OpenStack then document one-change-per-idea as house practice (`gerrit.md` §3). Sean Dague on OpenStack credits the pre-merge loop with "Coherent project culture" and says working without it "literally felt like developing in a thick sea of tar" ([dague.net](https://dague.net/2013/05/23/github-vs-gerrit/)).

**What GitHub does instead.** A PR is a branch of any size; the merge button squashes, and "When GitHub squashes commits, it concatenates the commit messages which is NOT what I want" (tylerhou, [HN](https://news.ycombinator.com/item?id=36608263)).

### 3. The author keeps building while the parent is in review

**Experience.** The reviewer gets a steady series of small, dependent changes instead of one late mega-change, and can review each independently. q3k calls it the first of "two killer features": "I will work on some feature, submit it for review as one CR, and then I can immediately start working on a feature that depends on that ... you can split large changes into multiple CRs, have them reviewed (possibly independently), then submit them all at once. It makes changes across large repos fantastically easy" ([HN](https://news.ycombinator.com/item?id=20500742)). Michael Große at Wikimedia valued "two small refactoring commits and one commit that does the behavior change" kept as separate reviews ([Talk:GitLab consultation](https://www.mediawiki.org/wiki/Topic:Vu7wk84g9qn855yu)). Ian Lance Taylor, on why Go stays on Gerrit: "Gerrit does a good job of handling stacked changes" ([golang/go #61182](https://github.com/golang/go/discussions/61182)). Matt Hall on the payoff: "you may not get the entire relation chain in at once - or at all - but you might get a few in which overall improve the product before the next release."

**Mechanism.** Git ancestry becomes the relation chain; each change lands on its own; a child shows its diff against its parent (`gerrit.md` §1).

**Tool or culture: tool.** The chain falls out of plain `git push` of a local branch.

**What GitHub does instead.** "On GitHub you can simulate this by changing the base of the PR yourself, but it's not as smooth experience" (viraptor, [HN](https://news.ycombinator.com/item?id=20503048)); lima: "More convenient than before, but nowhere near as convenient as keeping everything on a single branch so that it can be rebased in one go" ([HN](https://news.ycombinator.com/item?id=26847429)). Compass looked at "automatically pointing dependent pull requests, CLI/scripts for git rebasing" and found they "would require large efforts for minimal returns and would antagonize the Github tooling."

### 4. Every comment is a ticket that must be closed, and it follows the code

**Experience.** The reviewer can tell at a glance which of their concerns are still open, and the author knows exactly what is left to do. The Go contribution guide states the norm: "Think of each review comment like a ticket: you are expected to somehow 'close' it by acting on it, either by implementing the suggestion or convincing the reviewer otherwise ... You can click the 'Done' button to reply indicating that you've implemented the reviewer's suggestion" ([go.dev/doc/contribute](https://go.dev/doc/contribute)). Ian Lance Taylor: "Gerrit is good at supporting line-by-line code reviews, and tracks for each comment whether it has been addressed or not" ([golang/go #61182](https://github.com/golang/go/discussions/61182)). asb put it alongside Phabricator: "the ability to queue multiple comments up and submit them at once, mark previous things as fixed, keep track of a patch as it evolves" ([HN](https://news.ycombinator.com/item?id=12487695)). lima: "Inline comments aren't lost on rebases and will be ported" ([HN](https://news.ycombinator.com/item?id=26847429)). dietrichepp: "Merge approval can be made contingent on resolving minor issues within a diff" ([HN](https://news.ycombinator.com/item?id=24919815)).

**Mechanism.** Each thread is resolved or unresolved; "Done" and "Ack" are one-click replies; unresolved threads can block submit; unresolved threads are ported to later patch sets by shifting their line range (`gerrit.md` §1, §2.4). Joe Blubaugh adds an ordering benefit: "Review comments in Gerrit can be ordered as the reviewer desires, whereas Github comments are sorted by the order that they're added to the draft" ([golang/go #61182](https://github.com/golang/go/discussions/61182)).

**Tool or culture: both.** The resolved flag is tooling; "reply to every one" is Go's written rule.

**What GitHub does instead.** Conversations can be resolved, but after a force push comments may show as outdated (see `phabricator-experience.md` reason 3). Blubaugh: "Understanding the scope of the requested changes can be difficult in Github." Inference: Gerrit ports only *unresolved* threads, so the ticket model is about open work, not about remembering what was already approved (`gerrit.md` §2.4).

### 5. A vote says exactly what the voter checked

**Experience.** Nobody wonders what an approval means or who still has to act. jrockway: "+2 Code Review means I reviewed the code, +1 Verified means that I ran it and it worked. Those are different things and having to have both makes the responsibility clear, even if the author is adding +1 Verified" ([HN](https://news.ycombinator.com/item?id=20501697)). Matt Hall on the graded scale: "The negative numbers mean 'please don't submit this' and 'I'd prefer if you didn't submit this' respectively. Whereas the positive numbers mean 'looks good to me, but I would like someone else to review' and 'looks good, can submit'", which "helps to get sign-off for example if you are working on API changes that a consumer library need to make sure works for them but they don't have the authority to approve" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). mbbx6spp: "Github's PRs do not track the notion of review rating except loosely in the comments ... Gerrit's reviews do track this" ([gist](https://gist.github.com/mbbx6spp/70fd2d6bf113b87c2719)). q3k's second killer feature is the rule engine: "rules like 'product A must be approved by an owner of A but cannot be self-approved; in addition, someone who is fluent in the languages used must approve it, but that can be self-approval'" ([HN](https://news.ycombinator.com/item?id=20500742)). When ChromeOS made +2 survive trivial rebases, the announcement promised "you now will only have to re-review patches when the code actually changes" and a reply was "I would be sooooooooo happy" (quoted in `gerrit.md` §2.1).

**Mechanism.** Separate labels (Code-Review -2..+2, Verified -1..+1, site labels like Go's Hold), submit requirements as queries over labels, and per-label copy rules on a new patch set (`gerrit.md` §1, §2.1).

**Tool or culture: both.** The labels are tooling; what +1 obliges is culture. OpenStack treats a -1 as "obstructing someone else's work" and a +1 as helping "re-review any subsequent patch set more quickly" (`gerrit.md` §3).

**What GitHub does instead.** One Approve / Request changes / Comment state per reviewer, and CI status as a separate check; branch protection counts approvals but not what kind.

### 6. The tool tells you whose turn it is

**Experience.** Reviewers and authors stop polling. Gerrit's own user research found that "Not knowing whose turn it is has been identified by research as a reason for several time-consuming behaviors, such as adding more reviewers than necessary, checking the dashboard and bolded changes repeatedly or abandoning the dashboard completely" ([attention set use cases](https://www.gerritcodereview.com/design-docs/attention-set-use-cases.html)). The same document notes that before it, users leaned on email because it "provides a 'natural queue' of things to work on". Ian Lance Taylor: "Gerrit maintains an 'attention set' for who should look at the change next" and "provides dashboards of changes that need review by different people" ([golang/go #61182](https://github.com/golang/go/discussions/61182)). Michael Große liked a dashboard with "my WIP patches, my outgoing patches await review by peers, my incoming patches from peers awaiting my review" ([Talk:GitLab consultation](https://www.mediawiki.org/wiki/Topic:Vu7wk84g9qn855yu)). tylerhou: Gerrit "concisely shows the PR history and what each individual is working on" ([HN](https://news.ycombinator.com/item?id=36608263)).

**Mechanism.** A per-change attention set updated by replies, votes going stale and reviewer changes; a "Your turn" dashboard section with wait time (`gerrit.md` §1).

**Tool or culture: both.** The set is tooling; the doc's "If you don't plan to respond within ~24h" expectation and Chromium's feedback-three-times-a-day target are culture (`gerrit.md` §3).

**What GitHub does instead.** "Review requested" is a one-way flag that clears when you review; nothing says the ball is back with the reviewer after the author replies. This is the same gap `phabricator-experience.md` reason 7 records.

### 7. A reply is one composed act

**Experience.** The author answers all comments together, after the code is fixed, and the reviewer gets one coherent message. tylerhou: "I tend to write responses to comments while I edit code. When I'm satisfied and I've pushed my new code, I want to send all of the responses at once -- especially if two responses depend on each other. GitHub doesn't let me draft responses and then send all (unless I let the responses hang in the HTML input, which is risky)" ([HN](https://news.ycombinator.com/item?id=36608263)). asb: "queue multiple comments up and submit them at once" ([HN](https://news.ycombinator.com/item?id=12487695)).

**Mechanism.** Every comment is a draft until the Reply dialog publishes all drafts together with the vote (`gerrit.md` §1).

**Tool or culture: tool.**

**What GitHub does instead.** GitHub has "Start a review", which a reply to tylerhou pointed out: "You just comment and click 'add to review' as you go and then submit them all together at the end" (codeapprove, [HN](https://news.ycombinator.com/item?id=36608456)). The complaint that survives is about the author's side of the loop, where replies to existing threads are easy to send one by one.

### 8. You can see how far through a change you are

**Experience.** On a large change read out of order, the reviewer never loses their place. Martin Fick: "I use this feature EVERYTIME I review a change", and the "M" shortcut "not only marks a file 'reviewed', but also advances to the next 'unreviewed' file". Clark Boylan: "The 'reviewed' flag can help keep track of what you have looked at in larger changes when you are jumping from file to file." Adrià Vilanova Martínez: "I start by reviewing trivial changes to files and then take a look at the remaining unreviewed files" (all [repo-discuss](https://groups.google.com/g/repo-discuss/c/3ChEeECx7Ls)). q3k lists "marking of files as reviewed" among the reasons the UI is "much better ... for actually reading" ([HN](https://news.ycombinator.com/item?id=20500742)).

**Mechanism.** A private per-file checkmark per patch set, optionally set on view, carried to a new patch set only when the file's blob is byte-identical (`gerrit.md` §2.3).

**Tool or culture: tool.** Even Gerrit's designers found it underused: the Reviewed feature was "fairly hidden" with many users unaware of it ([attention set use cases](https://www.gerritcodereview.com/design-docs/attention-set-use-cases.html)).

**What GitHub does instead.** GitHub added a per-file "Viewed" checkbox in 2019 ([GitHub blog](https://github.blog/2019-07-01-mark-files-as-viewed/)), so this is the reason GitHub has closed most fully. Gerrit's edge left is the keyboard loop of mark-and-advance.

### 9. It is dense, fast and keyboard-driven, and you comment on exactly what you mean

**Experience.** For someone reviewing all day, the tool gets out of the way. q3k: "Snappy and compact code review experience (no space wasted for whitespace, avatars, pretty buttons). Full coverage with keyboard shortcuts" ([HN](https://news.ycombinator.com/item?id=24919786)), and "it seems to be optimized for daily use by programmers, not for onboarding speed. That's a tradeoff I'm very much okay with" ([HN](https://news.ycombinator.com/item?id=24919848)). lima: "It's really fast and there's keyboard shortcuts for everything" ([HN](https://news.ycombinator.com/item?id=26847429)). tylerhou: "For an interface I use regularly, I really want a condensed view" ([HN](https://news.ycombinator.com/item?id=36608263)). On precision, Matt Hall: selecting text prompts "press 'c' to comment", and "You can comment on anything you can select ... it is obvious how to comment on multiple lines as well as pick a single word - e.g. if it is a misspelt word in a comment" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). jrockway: "Gerrit lets you comment on specific parts of the line, rather than the entire line" ([HN](https://news.ycombinator.com/item?id=20501697)).

**Mechanism.** A compact diff table, single-key navigation (next file, next comment, mark reviewed, reply), and comments anchored to an arbitrary character range, including in expanded context.

**Tool or culture: tool.**

**What GitHub does instead.** Line-granular comments, and "if you have to click to expand the entire file, you can't comment on the expanded parts" (jrockway). tylerhou: "GitHub's UI has so much whitespace that is definitely prettier but not useful for a tool that should help my productivity."

### 10. The commit message is reviewed as code

**Experience.** The why is part of what gets reviewed, so it is actually written. lima's first reason: "Ability to review commit messages (they're part of the codebase!)" ([HN](https://news.ycombinator.com/item?id=26847429)). Matt Hall: "The first 'file' in the changed list is the commit message. This reinforces the idea that the git history of your repository is something worth consulting", contrasted with a PR's "massive text box" that is either empty or a template "I don't bother to read because looking at the code is almost always quicker"; context "should live in either the commit message or in documentation around your code - not in some other company's database!" ([mattjhall.co.uk](https://mattjhall.co.uk/posts/software-i-love-gerrit.html)). tylerhou: "I care about my commit messages being precise and accurate."

**Mechanism.** The commit message is shown as a reviewable "magic file" first in the file list, with inline comments like any file (`gerrit.md` §1).

**Tool or culture: both.** The file is tooling; the expectation that a message explains the change is project style.

**What GitHub does instead.** The PR description is a separate, editable field outside git, on a separate tab from the diff; commit messages are not commentable, and squash-merge concatenates them.

## What people disliked

- **The UI, especially for people who do not live in it.** "the interface is written by developers with little knowledge of user experience" (huskyr, [HN](https://news.ycombinator.com/item?id=24919826)); "I had to use Gerrit in a previous job, and _hated_ it. The UX is abysmal. Some folks loved it though, especially engineers working mostly on the backend" (okhan, [HN](https://news.ycombinator.com/item?id=24922825)); "Git's CLI is like 10x superior to Gerrit's interface" (labster, [HN](https://news.ycombinator.com/item?id=16364439)); "it looks and feels like an unpolished jQuery + Bootstrap UI made in 2012" (wyqydsyq, [gist](https://gist.github.com/mbbx6spp/70fd2d6bf113b87c2719)); "GitHub's PRs and even Microsoft's internal tool ... are about 5x more pleasant to use subjectively" (lostmsu, [HN](https://news.ycombinator.com/item?id=27279286)). Even a fan: "I absolutely hated Gerrit when I was first introduced to it" (zipperhead, same thread).
- **It drives newcomers and drive-by contributors away.** "Any time I come across a project that uses Gerrit I immediately abandon any proposed patches I had planned to submit" (Washuu, [HN](https://news.ycombinator.com/item?id=16364439)); "Gerrit is so off-putting to new users that many never get over the learning curve ... it is almost universally disliked by newcomers. When your users are volunteers, you can't force them to use Gerrit until they get used it it" (20after4, Wikimedia, [HN](https://news.ycombinator.com/item?id=24921758)); "I have to Google on how to do basic stuff" (alessioalex, [HN](https://news.ycombinator.com/item?id=24928823)); "Try to create a code change within the web interface, without reading the docs" (AKlapper, [Talk:GitLab consultation](https://www.mediawiki.org/wiki/Topic:Vu7wk84g9qn855yu)). Go's own numbers and Eclipse's "where the developers are" are in `gerrit.md` §3.
- **The amend workflow fights ordinary git habits.** "I like to do frequent commits on short lived branches and using vanilla git" (dionian, [HN](https://news.ycombinator.com/item?id=24919913)); "Every minor change required amending a commit and another review" and it "really breaks a lot of the git process" (djsumdog, [HN](https://news.ycombinator.com/item?id=11429915)). Helpers did not fully fix it: "git-review tends to break in unclear ways" (bawolff, [HN](https://news.ycombinator.com/item?id=24926005)).
- **One commit at a time is a cost, not only a benefit.** Dogtag PKI: complex changes must be "broken into smaller incremental patches which takes more time to develop and test, or be submitted as a single large patch which makes it more difficult to review", and "The CI will once run for each patch, lengthening the total test time" ([dogtagpki.org](https://www.dogtagpki.org/wiki/Gerrit_vs_GitHub_Pull_Request)).
- **Keyboard ownership and bugs.** "overriding ctrl-f in the browser but then having the overriden search bar not work or not being able to effectively type inline comments on mobile" (bawolff, [HN](https://news.ycombinator.com/item?id=24926027)).
- **It is slow to merge in practice.** "Any project that users gerrit for some reasons takes 10x+ time to merge issues or communicate" (AndyNemmity, [HN](https://news.ycombinator.com/item?id=16364439)). Inference: this is a culture effect of strict gates as much as a tool effect.
- **You have to run it yourself, and integrations lag.** Self-installation is "definitely a little obtuse and unforgiving" (zzzeek, [techspot.zzzeek.org](https://techspot.zzzeek.org/2016/04/21/gerrit-is-awesome/)); "Gerrit service is not very reliable. Sometimes it's not available" (Dogtag PKI); Compass left partly to "offload in-house maintenance burden" and because GitHub "integrates seamlessly with CircleCI" ([Compass](https://medium.com/compass-true-north/from-gerrit-to-github-cebc463ec01b)).
- **Turn rules are not always obvious.** At the attention set trial, Matthias Sohn did "not understand why everybody (authors and reviewers) seem to have the next turn at the same time" ([repo-discuss](https://groups.google.com/g/repo-discuss/c/bOvYWaYgbAI)).

Inference: the split matches `gerrit.md`'s conclusion. The *mechanisms* in reasons 1 to 8 are praised even by people who left (Compass calls losing them "the biggest hesitation"), while the *surface* (UI, push workflow, self-hosting, separate site) is what people left over.

## Implications for hihyou

Inference throughout; each item cites the reason it comes from.

1. **Make patch-set compare the default for round two, and go below the file.** Reason 1 is the most-cited strength and GitHub's most-cited gap. hihyou's M4 already plans any-two-version compare with rebase noise tinted, and M4's base-moved-versus-author-changed split is the rebase tint. The rerere-style verdict carry keyed per AST-node edit `(anchor, before hash, after hash)` is the step beyond Gerrit: Gerrit carries votes per commit and checkmarks per byte-identical file, so one conflict hunk resets everything (`gerrit.md` §2.1, §2.3). hihyou should also make "re-check" visible, the state Gerrit never produces.
2. **Read per commit without asking authors to split differently.** Reasons 2 and 3 are why reviews felt small, but Gerrit bought them with the amend workflow people disliked. Per-commit reading over an ordinary PR or range gives the reviewer the one-idea unit from history that already exists; the M4 commit accordion keeps each commit's message beside the hunks it made, which is also reason 10 without a magic file.
3. **Treat reviewed state as the reader's progress, and derive approval from it.** Reasons 4, 5 and 8 are the same wish at three sizes: a comment closed, a file checked, a change approved. hihyou's verdicts per node are the finest version of Gerrit's reviewed checkmark; per-layer approval derived from those verdicts replaces a vote the reviewer must remember to re-cast. Carry resolved verdicts, not only open threads, since Gerrit ports only unresolved comments (`gerrit.md` §2.4). Keep Gerrit's mark-and-advance loop (Martin Fick's "M") as the keyboard path: next unverdicted node, not next file.
4. **Let the verdict say what was checked, but keep the set small.** Reason 5 (jrockway's "I reviewed" versus "I ran it") argues for a verdict kind; YAGNI says start with one kind ("read") and add another only when a host or user brings a second claim.
5. **Spend the reviewer's attention only on what M2 cannot explain.** Gerrit hides one proven class, rebase-only files. hihyou's M2 pipeline (normalize, approved rules, then moved / moved-and-edited / changed) and auto-folded generated files and lockfiles extend the same "hide only what is proven" idea to far more classes, and must show what was hidden to avoid Gerrit's hazardous rebase (`gerrit.md` §2.2).
6. **Follow GitHub's comment UI, and draft by default.** Reason 7 is covered by M6's "Add single comment" or "Start a review". For a Diffset with no host, drafts stay in the browser, which gives tylerhou's "send all of the responses at once" for free.
7. **Dense and keyboard-first, without stealing browser keys.** Reason 9's praise and bawolff's Ctrl-F complaint come from the same design; hihyou should bind review keys but leave browser find working, which also serves `phabricator-experience.md` reason 9 (never-silent collapse that Cmd-F can search).
8. **Leave the turn-taking queue to the host.** Reason 6 is loved but belongs to a review platform with identities and notifications; hihyou can show a host's "your turn" data when an adapter exposes it. For Gerrit hosts, a browser-only adapter cannot call the REST API cross-origin and must read `refs/changes/*` via git or a user proxy (`gerrit.md` §5).
9. **Require no workflow change.** Every dislike except the UI is about what Gerrit demands of authors (amend, one commit, push to a magic ref, a separate site). A viewer over existing commits, ranges and PRs keeps reasons 1 to 5 and 8 to 10 and skips the part that drove Wikimedia, Eclipse and Compass away.

# JetBrains Upsource: model, code intelligence in review, and why it ended

Research for hihyou (platform-agnostic diff-set viewer). The problem, in the user's words: "just seeing sequence of diffs without any intention makes user 피로 (fatigue). reviewing on github makes us 피로. seeing pr on vs code is a way better. but not enough." Upsource is the closest historical answer to the VS Code half of that remark: a review tool that ran the IntelliJ analysis engine on the server so the browser diff had navigation, find usages and inspections. It was sold from 2014 to January 2022. The live help is gone; help pages are cited from web.archive.org copies. Comparisons point at `gerrit.md` by section. Claims are tagged **[fact]** (read in JetBrains docs, a JetBrains blog post, a JetBrains support reply, or a first-hand post) or **[inference]** (my reasoning from those facts).

## Short answer

- **Model.** A review is a server-side entity over a *set of revisions* (commits) or a whole branch, not over a branch diff. Revisions are added to an open review by hand, by an issue or review ID in the commit message, or automatically for a branch review. Reviewers end with Accept or Raise concern per review; the review is "Completed" when every reviewer has done one of the two, and closed by the author. Reviews are post-commit only.
- **Code intelligence.** Upsource indexed every revision with the IntelliJ engine: go to declaration, find usages, "usages diff", type hierarchy and IntelliJ inspections in the review diff, for Java, Kotlin and JavaScript (PHP and Python were added later). That is the feature users and JetBrains both led with, and the one that cost the most memory and setup.
- **Carry.** Adding revisions shows the reviewer only the new revisions' diff, with a revision selector to toggle any subset; files carry a per-reviewer read mark; discussions live in the review and stay visible "throughout the different revisions". Upsource 2017.1 added squash/rebase tracking. There is no documented line-porting algorithm, and a support reply said force-push was "not supported by Upsource" and comments "might be lost".
- **End.** JetBrains stopped sales on February 1, 2022, citing an "industry trend of moving away from standalone code review tools", and pointed users to Space. Space was itself discontinued in 2024 and its code-review-only successor, SpaceCode, was dropped before general availability, so the lineage ends with no JetBrains review server.
- **For hihyou.** Upsource proves that IDE-grade navigation inside a review diff is what people remember, and that commit sets (not branches) as the unit fit trunk-based teams. It also shows the price of doing semantic analysis on a server per revision. hihyou can take the semantic reading and the only-what-is-new diff without owning a build model for every revision.

## 1. Model

### Review, revisions, branch review

**[fact]** "A code review in Upsource can be associated with one or more revisions, or an entire branch. Once initiated, a code review becomes a separate entity with a unique ID" ([codereview](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview.html)). The glossary defines a review as "A task that is associated with one or more revisions or branches" ([glossary](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/glossary.html)).

**[fact]** "Upsource supports post-commit reviews, which means you should commit a change to your VCS repository before a review can be initiated." Roles are author, reviewer and watcher, and "The commit author is always considered the author of the review, no matter who actually creates the review." ([codereview](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview.html)). The IDE plugin says the same: "A code review will be created only after the change has been pushed." ([ide-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/ide-author.html)).

**[fact]** Upsource 1.0 (December 2014) was an on-premises repository browser and review tool for Git, Mercurial, Subversion and Perforce that let teams "create code reviews on individual revisions or entire branches" ([1.0 release](https://blog.jetbrains.com/upsource/2014/12/09/jetbrains-upsource-1-0-is-released-available-for-purchase/)).

**[fact]** Two branch-shaped kinds exist beside the revision-set review: "Branch review — created to track and review ongoing changes in a selected branch. Every new commit to the branch is automatically included in the review." and "Merge review — lets you compare and review changes in selected branches before merging them." "A branch review cannot be created for a branch set as default." ([review-branches](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/review-branches.html)). A GitHub pull request is mirrored as a branch or merge review ([synchronizing-your-activities-in-github-projects](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/synchronizing-your-activities-in-github-projects.html)).

**[fact]** A revision belongs to at most one review. Asked for a revision in two reviews, JetBrains' Artem Rokhin replied: "If we decide to go this way there will be a situation when the same revision has "accepted" status in review A and "rejected" status in review B", then "From the architectural perspective the revision also might have accepted/rejected status", and "So, I am afraid, that multiple reviews for a single revision is not something we might implement in the nearest future." The workaround offered was a branch review ([support thread, 2016](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/207079495-Allowing-revisions-to-be-present-in-multiple-code-reviews)).

**[inference]** Compared with Gerrit (`gerrit.md` §1), Upsource's unit is looser: a Gerrit change is one commit revised as patch sets, while an Upsource review is a growing set of commits that are never rewritten by the tool. "Iteration" in Upsource means *more commits*, not *a new version of the same commit*. That is why trunk-based teams liked it (commits can be picked from anywhere) and why rebase and squash were a late, partial addition (§2.4).

### Adding revisions

**[fact]** The author's loop: "Work on resolving the issues, commit the fixes, and add the new revision(s) to the existing review." and "This way the whole discussion and revision history is contained within one review, and as long as the review is open it will always be visible throughout the different revisions." Revisions from other committers add those committers as authors ([codereview-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-author.html)).

**[fact]** Automation: Upsource 2.5 added "When an issue ID or review ID is present in the commit message we automatically attach the revision to the matching review if it's open" ([2.5 what's new](https://web.archive.org/web/2015/http://www.jetbrains.com/upsource/whatsnew/)). Custom workflows later covered creating reviews automatically, adding revisions by review or issue ID, assigning participants, and "Close a review when all participating reviewers accept the changes." ([custom-workflows](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/custom-workflows.html)). Upsource 2017.2 added "Suggested Revisions in Reviews", using "advanced statistical analysis to suggest revisions that should be added to a review" ([2017.2](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-2/)); 2017.1 added review suggestions of the form "Steve Jones owns the modified files. Create review?" ([2017.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-1/)).

**[fact]** Branch reviews prune: a support reply explained that "When a new commit appears in the branch, Upsource goes through all revisions attached to the branch review and delete those which are not unique for the branch. Unfortunately it also happens to revisions that were manually added to the review." and that this happens "when branch got merged into another, and the removed revisions are no more unique to the given branch" ([support thread, 2015](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/206577195-Upsource-just-removed-21-revisions-from-a-review-and-I-don-t-know-why)).

### Reviewer states and completion

**[fact]** "If you're satisfied with the changes and consider your work done, press Accept . If you find them questionable, press Raise concern ." ([codereview-reviewer](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-reviewer.html)). Upsource 3.0 renamed Reject: "The "Reject" action has been renamed to "Raise concern". Click "Accept" when you're done reviewing a change and no further actions from the code author is required. Use "Raise concern" when you've discovered a problem that needs to be addressed, or you have questions that need to be answered." ([3.0](https://web.archive.org/web/2020/https://www.jetbrains.com/upsource/whatsnew/3-0/)).

**[fact]** Review statuses: "Pending — review is created and reviewers assigned.", "Completed — all reviewers completed the review by raising concern about or accepting your changes." and "Closed — review is closed by its author, as no further action is required or expected from all participants." "If a default deadline has been set, it will be automatically moved when new revisions are added or new reviewers join the review." ([codereview-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-author.html)). The reviews list filters by Created, Assigned, "Has concern", Mentioned and Completed ([reviews-available](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/reviews-available.html)). Predefined review labels are "Work in progress" and "Ready for review" ([review-labels](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/review-labels.html)).

**[inference]** Against Gerrit's labels (`gerrit.md` §1): Upsource has one binary-ish verdict per reviewer, no numeric scale, no veto that survives new revisions, and no submit rule; Completed means everyone answered, not that everyone approved. Close is a human act, optionally automated by the close-when-all-accept workflow. There is no separate "Verified" claim from a person; CI status is a build badge (§6).

## 2. Carry across iterations: what the reviewer sees again

### 2.1 Only the new revisions

**[fact]** "When new revisions are added to the review, you only see the diff of those revisions. If you want to show or hide any additional revisions within a review, use a revision selector that quickly toggles revisions on and off" ([codereview-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-author.html)). The reviewer page says the reviewer "can proceed with reviewing without having to inspect previously committed changes once again." ([codereview-reviewer](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-reviewer.html)). The IDE plugin has the same revision checkboxes ([ide-manage-reviews](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/ide-manage-reviews.html)) and, from 3.0, a "Smart summary diff : in reviews containing multiple commits it can show only new changes instead of a full diff between first and last revisions." ([3.0](https://web.archive.org/web/2020/https://www.jetbrains.com/upsource/whatsnew/3-0/)).

**[inference]** Because revisions are commits that are never amended, changes since last review are simply the commits added since, a set difference. That is cheaper and more exact than Gerrit's patch-set-to-patch-set compare (`gerrit.md` §2.2), which must tint rebase edits, but it only works while nobody rewrites history.

### 2.2 File read marks

**[fact]** Upsource 2.5 showed unread files in bold ([2.5 what's new](https://web.archive.org/web/2015/http://www.jetbrains.com/upsource/whatsnew/)); a progress bar shows how many files each reviewer has opened ([codereview-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-author.html)); 2018.1 added "Mark file as unread" ([2018.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2018-1/)), and 2017.3 "Mark code review as unread" ([2017.3](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-3/)).

**[inference]** The docs do not say whether a read mark resets when a later revision touches the file. Gerrit's checkmark copies only for a byte-identical blob (`gerrit.md` §2.3); Upsource's rule is unknown (see Unverified).

### 2.3 Discussions and anchoring

**[fact]** Three comment kinds: review, code selection and line. "Posted code selection comments and line comments are embedded in code and highlighted with yellow." "When a discussion thread comes to a logical end, either you or the reviewer can mark it as resolved." Comments take Markdown, attachments, reactions, labels and task lists ([discussion-comments](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/discussion-comments.html)); predefined discussion labels are bug, code style, enhancement and help wanted ([discussion-labels](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/discussion-labels.html)). Comments can also be left on a revision with no review: "These comments are posted from the revision page and are considered part of the revision." ([comment-without-review](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/comment-without-review.html)). From the IDE: "Your comment will be attached to the latest revision." ([commenting-from-the-editor](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/commenting-from-the-editor.html)).

**[fact]** Upsource 2.5 added a review timeline option for "showing only unresolved discussions" ([2.5 what's new](https://web.archive.org/web/2015/http://www.jetbrains.com/upsource/whatsnew/)); 2017.3 added a discussions filter in all code views that can hide resolved ones ([2017.3](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-3/)); 2018.1 added filtering by discussion label, "which should improve handling of large, long-lived reviews" ([2018.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2018-1/)); 2017.1 added "Resolve discussions automatically" on close ([2017.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-1/)).

**[fact]** On anchoring across revisions, the only direct claim is a vendor one, from a self-described Upsource team member: "Upsource has sticky comments that survive code changes well." (leonya2, [HN 13021784](https://news.ycombinator.com/item?id=13021784)). A 2014 Habr overview (in Russian) says discussions have unlimited lifetime and that an unanswered discussion on an old revision is shown to reviewers again the next time the file is reviewed ([Habr](https://habr.com/en/articles/232985)); paraphrased here, not quoted.

**[inference]** The mechanism differs from Gerrit's porting (`gerrit.md` §2.4). Gerrit copies unresolved comments onto the new patch set by shifting line ranges. Upsource needs no porting for ordinary iterations, because the old revision still exists in the review: a comment stays on the revision it was made on, and the review keeps it visible. Nothing in the docs describes how a line comment is re-placed on a later revision of the same file, so "survive code changes" is unproven beyond the vendor's word.

### 2.4 Rebase and squash

**[fact]** Before 2017, a support reply on rebased branches: "Force push is not a best practises scenario and not recommended for usage. Thus it's not supported by Upsource. Branch review and code comments might be lost in such case." Asked to re-home comments onto the rebased revision: "We are not sure yet how to technically handle this scenario.." ([support thread](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/206578335-How-are-rebased-branches-handled)).

**[fact]** Upsource 2017.1: "Squash/rebase support Upsource now supports squashed Git commits (revisions), and updates the history to display new commit ids and new commit messages from the VCS. Review timeline also reflects the reasons old revisions have disappeared from the review." ([2017.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-1/)). A later support reply: "if you do branch squash in git (to a single commit), Upsource will transplant all review's discussions accordingly." ([support thread](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/360000004370-Squash-merge)).

**[fact]** There was no squashed view of a WIP branch. Asked "is there a way such that the reviewers do not see the changes among the WIP commits?", the only answer was a user's workaround of committing the final state onto a separate review branch ([support thread](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/360000524444-How-to-let-reviewers-see-a-squashed-view-)). Renames across distant folders in Mercurial showed "up as a file removal and addition" (2018.2, [support thread](https://web.archive.org/web/2022/https://upsource-support.jetbrains.com/hc/en-us/community/posts/360005568299-File-move-showing-up-as-an-add-and-remove-in-Upsource-Review)).

**[inference]** Against `gerrit.md` §2.1 and §2.2: Gerrit keys carry on a whole-commit change kind and tints rebase edits; Upsource's model assumed commits are immutable, then learned to map a squash onto the old revisions and move discussions. Neither keys anything on the edit. Upsource never carried a verdict across a rebase in a documented way; Accept is per review, not per revision or edit.

### 2.5 Against the rerere-like idea

The idea (from issue #26, as first filed): a verdict per edit keyed on `(anchor, before hash, after hash)`; same edit and same context carries; same edit and changed context flags "re-check"; changed edit shows only its interdiff.

| hihyou case | Upsource |
|---|---|
| Same edit, same context, carry verdict | Holds trivially while commits are only added: old revisions and their discussions stay in the review; the reviewer is shown only new revisions. No per-edit verdict exists. **[inference]** |
| Same edit, changed context, "re-check" | Not flagged. A new commit elsewhere that changes the edit's context appears as its own revision; nothing links it to earlier accepted code. The usages diff (§3) is the nearest tool, and it is on demand. **[inference]** |
| Changed edit, show only interdiff | Natural for fix-up commits (the new revision *is* the interdiff); after a squash or rebase, 2017.1 maps revisions but the docs show no edit-level interdiff. **[fact]** [2017.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-1/) |

**Where it breaks** (**[inference]** from §1 and §2.4): a revision in two reviews is impossible; a branch review drops revisions once they stop being unique to the branch; force-push before 2017.1 could lose comments; a rename across folders reads as delete and add.

## 3. Code intelligence in the browser

**[fact]** Origin: Upsource came from making the IntelliJ platform "available in a headless way"; the 2013 announcement's diagram centers on "IntelliJ IDEA Code Analysis engine, analyzing your source code and detecting the same issues you see in your IDE, in the browser." ([Upsource, a platform](https://blog.jetbrains.com/upsource/2014/10/10/upsource-a-platform/)). The 1.0 release promised Java code insight "as if you were using IntelliJ IDEA" ([1.0 release](https://blog.jetbrains.com/upsource/2014/12/09/jetbrains-upsource-1-0-is-released-available-for-purchase/)).

**[fact]** "Upsource provides server-side code intelligence with its built-in static analysis engine. It supports Java, JavaScript, and Kotlin projects that use IntelliJ IDEA, Maven, or Gradle as their build system." The inspection profile comes from the project's `Project_Default.xml`; "Code inspections are available in all views."; a sidebar marks each file green, red or yellow ([display-code-inspection](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/display-code-inspection.html)). Python came in 2017.2 alongside external engines (SonarQube, ReSharper) ([2017.2](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2017-2/)); results from TeamCity's IntelliJ and ReSharper inspections could be uploaded ([external-inspections-support](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/external-inspections-support.html)). Project setup warns that "code intelligence is applied to every revision and may contribute to slow indexing and page load performance, especially in big projects" ([creating-a-project-code-intelligence](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/creating-a-project-code-intelligence.html)).

**[fact]** Navigation in all three views (inline diff, side-by-side, file): quick documentation, find usages, and "View usages diff": "All usages of that element in the file will be listed with an indication of which of them were added between the two revisions, which were removed and which weren't changed". Go to declaration, hierarchy and highlight usages were side-by-side and file view only ([navigate-in-file](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/navigate-in-file.html)). Upsource 3.0 announced "Find usages works everywhere!", adding it to the review diff ([3.0](https://web.archive.org/web/2020/https://www.jetbrains.com/upsource/whatsnew/3-0/)), plus a Code Analysis Summary that "shows you the issues that were introduced or fixed in the changes you're looking at" (same page).

**[fact]** JetBrains' own pitch, by Trisha Gee: "As a developer, code reviews can sometimes be a frustrating process – you're used to all the power of your IDE, yet when you open up a set of changes in your code review tool you can't leverage any of that. The cognitive load of having to navigate through the code in an unfamiliar way and losing all the context your IDE provides is one of the things that makes developers less keen to perform code reviews." Find usages matters "because if a method or class has been changed in some way, you as the reviewer want to see what the impact of this change is"; navigation "lets you browse through the code in a way that's natural for you, rather than having some arbitrary order imposed on you"; and "Inspections are not infallible, hence why they're useful pointers for reviewers but not a fully automated check with a yes/no answer." ([Upsource Quick Wins](https://blog.jetbrains.com/upsource/2015/10/19/what-to-look-for-in-a-code-review-upsource-quick-wins/)).

**[inference]** Gerrit has nothing comparable (`gerrit.md` §4, pillar 4: review happens in a web diff table without navigation). Upsource is the existence proof that the review-only editor pillar was built and used at scale, and the usages diff is a primitive version of the same-edit, changed-context case: it answers which usages a change added or removed, though only within one file and only when asked.

## 4. Diff views

**[fact]** Three ways to read a change: inline (unified), side-by-side, and compare ([diff-ways-to-compare-code](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/diff-ways-to-compare-code.html)). "The unchanged blocks of code are hidden by default. You can reveal them by clicking on the cut lines" ([side-by-side-diff](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/side-by-side-diff.html)). The compare page takes any two revisions, branches or tags, with Commits and Files tabs ([compare-page](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/compare-page.html)). Merge reviews show conflicts: "Files with conflicts that cannot be resolved automatically are highlighted in red." ([review-branches](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/review-branches.html)); 2019.1: "Merge reviews let you check the changes that will be merged into the selected branch and find any conflicts before merging." ([2019.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2019-1/)).

**[fact]** Upsource 3.0 let projects exclude files by wildcard, naming "Assets, generated code, test data" ([3.0](https://web.archive.org/web/2020/https://www.jetbrains.com/upsource/whatsnew/3-0/)).

**[inference]** Revision range selection is the revision selector (§2.1) plus the compare page; there is no patch-set-pair picker like Gerrit's (`gerrit.md` §1) because there are no patch sets.

## 5. IDE plugin

**[fact]** The plugin "allows you to participate in code discussions and manage reviews without leaving your IDE" and supported IntelliJ-platform IDEs 2016.1+ and Android Studio 2.2 ([codereview-ide-plugin](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/codereview-ide-plugin.html)). Authors create reviews from the VCS Log or the Commit dialog ([ide-author](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/ide-author.html)); reviewers toggle revisions, "Compare this file version with your local version", and "Jump to source" ([ide-manage-reviews](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/ide-manage-reviews.html)). 2.5 added the reverse direction: "Version 2.0 introduced an IDE plugin... In 2.5 we are providing integration in the opposite direction — it is now possible to open a review ... in the IDE" ([2.5 what's new](https://web.archive.org/web/2015/http://www.jetbrains.com/upsource/whatsnew/)). JetBrains itself reviewed this way: "At JetBrains we do code reviews using either Space or Upsource plugin right in IntelliJ IDEA" (Yuriy Artamonov, [dev.to](https://dev.to/jreznot/comment/1l8le)).

**[inference]** The plugin reviewed in the user's real, locally built project, so the IDE supplied code intelligence for free there; the server engine existed for the browser. That split is the user's VS Code remark in product form.

## 6. TeamCity and CI

**[fact]** "Integrating with a TeamCity CI server is provided via a Commit Status Publisher plugin which comes bundled with the TeamCity version 9.1.7 and newer." Other CI servers post JSON to a build status endpoint with state in_progress, failed or success ([ci-server-integration](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/ci-server-integration.html)). TeamCity's IntelliJ and ReSharper inspection results could be pushed in as external inspections ([external-inspections-support](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/external-inspections-support.html)).

**[inference]** Against Gerrit's `Verified` label (`gerrit.md` §1): Upsource showed build status per revision but did not make it a vote or a gate; there was no submit rule to gate.

## 7. Analytics

**[fact]** Analytics covered commit activity, a project treemap, file history, code review coverage and a reviewers graph ([analytics-main](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/analytics-main.html), [analytics-code-review](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/analytics-code-review.html)). The code ownership report flags files "exclusively authored by one person until another person made changes to it recently" and files with more than 6 authors ([code-ownership-report](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/code-ownership-report.html)). "The more two people review each other's changes, the thicker the link between them becomes." ([reviewers-graph](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/reviewers-graph.html)). An introduced-and-fixed-issues report tracked inspection results over time ([introduced-and-fixed-issues-report](https://web.archive.org/web/2021/https://www.jetbrains.com/help/upsource/introduced-and-fixed-issues-report.html)). 3.5 added "Review Time Statistics" ([3.5](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/3-5/)).

## 8. Discontinuation, Space, and Space's end

**[fact]** "As of February 1, 2022, we will no longer sell new licenses or renewals", with "technical support and critical security updates until January 31, 2023." Stated reason: "a gradual industry trend of moving away from standalone code review tools to those integrated with other areas of software development." and "we tried to offer integration of Upsource with our other teamware tools. However, we realized that not only was this limiting what we could achieve, especially in terms of a pleasant user experience, but it also created additional installation and maintenance burden for end users. As such, we decided to focus our efforts around code review on JetBrains Space" (Elena Pishkova, [end-of-sales announcement](https://blog.jetbrains.com/upsource/2022/01/31/upsource-end-of-sales-announcement/)).

**[fact]** JetBrains' own Q3 2021 comparison (a PDF) marked only Upsource and Space as supporting per-commit review of random commits, against GitHub, GitLab and Bitbucket; Upsource alone had discussion labels and server-side code analysis; Space supported Git only, while Upsource also read Mercurial, SVN and Perforce ([Space Code Review Comparison](https://resources.jetbrains.com/storage/products/space/docs/Space_Code_Review_Comparison.pdf)).

**[fact]** Space ended two years later. "many organizations have their own specific needs, processes, and existing systems", "we had a substantial number of users asking us to integrate Space with third-party tools such as Slack, as well as with our own tools like YouTrack and TeamCity", and "the adoption of Space has not been what we had hoped for". Sales stopped May 28, 2024, with support through May 31, 2025, and Space pivoted to SpaceCode, "Git hosting and code reviews" only ([The Future of Space](https://blog.jetbrains.com/space/2024/05/27/the-future-of-space/)). Six months later: "In light of user feedback and current market trends, we've decided not to make SpaceCode generally available." Cloud access ended June 1, 2025; on-premises may run indefinitely ([SpaceCode discontinuation](https://blog.jetbrains.com/space/2024/11/27/discontinuation-of-the-spacecode-private-preview/)). DevClass reported customers "deeply disappointed" ([DevClass](https://www.devclass.com/ci-cd/2024/05/28/customers-protest-as-jetbrains-ends-space-collaboration-platform-intros-spacecode-as-partial-alternative/1631438)).

**[inference]** The two announcements give opposite reasons: Upsource was closed because a standalone tool was a poor fit for integration, and Space because teams wanted integration with the tools they already had. The mechanisms users missed (commit-set reviews, IDE-grade navigation) did not carry into the successors; `upsource-experience.md` collects those reactions.

## 10. Gaps against hihyou's four pillars

1. **Review by AST node.** Upsource had the AST (the IntelliJ PSI) on the server and used it for navigation and inspections, but review state was per review (Accept), per file (read mark) and per line or selection (comments). It never attached a verdict to a syntax node. **[inference]** from §2 and §3.
2. **Verified grouping and hiding.** Only by filename wildcard ("Assets, generated code, test data") and, in merge reviews, conflict highlighting; no grouping of moved or mechanical edits, and a far rename read as delete plus add. **[fact]** §4, §2.4.
3. **Organization by intention.** Reviews collect commits, and a review has a description (2019.1) and labels, but nothing inside a review groups edits by intent; order is the file list or the reviewer's own navigation, which Trisha Gee called the point. **[inference]** from §3 and [2019.1](https://web.archive.org/web/2021/https://www.jetbrains.com/upsource/whatsnew/2019-1/).
4. **Review-only editor.** The strongest match of any tool surveyed: navigation, usages, usages diff, hierarchy and inspections inside the review diff, plus an IDE plugin. **[fact]** §3, §5.

## 11. Implications for hihyou

- **IDE-grade reading is the remembered feature; ship it where it is cheap.** Upsource paid for it with a JVM indexing every revision, which is what users disliked. hihyou can get go-to-definition and find usages from a language server or tree-sitter over the two sides of one diff, not a full project model per revision. **[inference]** from §3 and §9.
- **A usages diff is a ready-made "re-check" signal.** Usages added, removed or unchanged between two revisions are exactly the context change that should flag an unchanged edit for re-check; hihyou can compute it proactively rather than on click. **[inference]** from §3.
- **Accept any commit set, not only a branch.** The most-missed trait is reviewing commits picked from anywhere. hihyou's Diffset over arbitrary ranges and commits already fits; do not require a PR or branch. **[inference]** from §1 and §9.
- **Showing only what is new to the reader should survive rewrites.** Upsource's cheap set-difference worked until history was rewritten, then comments "might be lost". hihyou's content-keyed `(anchor, before hash, after hash)` carry is the rewrite-proof version of the same experience. **[inference]** from §2.1 and §2.4.
- **Let one edit appear in two review contexts.** Upsource refused because a revision would carry two statuses. hihyou's verdicts belong to the reader and the edit, so the same edit in two Diffsets can share one verdict. **[inference]** from §1.
- **Keep Accept and Raise concern as the per-review summary, derived from verdicts.** Upsource's two-state end (and Completed meaning that everyone answered) is simpler than Gerrit's scale and matched what people used. **[inference]** from §1.
- **Do not become a server.** Both of JetBrains' stated reasons, a standalone tool's "installation and maintenance burden" and teams keeping "existing systems", argue for hihyou's viewer-over-existing-hosts shape. **[inference]** from §8.

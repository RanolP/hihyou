# The syntechs formatter: design decisions

The formatter in `packages/syntechs/src/fmt` lays out code for display in review (see `docs/design/product.md` ("Diff model") for why viewers reformat at all). This page records the decisions that fix its shape. `docs/research/formatter.md` is the earlier survey; its recommendation of a dprint-core port driven by interpreted rules was superseded by the generated stream code described here.

## Whose style: repo config, then the reviewer's overrides

The formatter reads prettier and ruff configuration under those tools' own option names: "the formatter shall be aware of prettierrc or ruff config." Precedence is per option: the formatter's defaults, then the repo's `.prettierrc` or ruff config, then only the options the reviewer explicitly set ("respect user's one if overriden"). An option the reviewer never set comes from the repo. `packages/present/src/format-config.ts` implements the discovery and the merge.

Stylistic token rewrites that keep meaning are allowed: quotes, semicolons, trailing commas, redundant parentheses, number and hex normalization. "stylistic changes (e.g. singleQuote) shall be acceptable since it doesn't replace semantics."

## The tree is the only input

The formatter never sees the original source string: "나는 포매터가 원래 소스코드 문자열을 볼 방법이 없으면 좋겠어. 애초에 AST만이 입력인 거야" (the formatter should have no way to see the source string; the AST is its only input). It is a pure function of the tree, so everything it needs comes from the tree API rather than from slicing or lexing the source.

- The input type enforces this. `FormatTree` (`packages/syntechs/src/fmt/tree.ts`) is the arena `Tree` without offsets or source.
- Token text comes per leaf. A node whose text is not covered by child leaves (CSS `float_value`, for example) must become a token.
- Line breaks come from `lf(node)`: the number of newlines before the node's first leaf, counted around comments. It is a function rather than `[lf, n]` entries in the children list, because line breaks are everywhere and every children loop would otherwise have to filter them out. Spaces and indentation are not exposed, and the formatter needs no positions.

## Correct by construction, checked by tests

The formatter is treated like a compiler: correct by construction, with bugs caught by tests. `format` never checks its own output. The checker is a separate function, `check(language, prev, formatted)` in `packages/syntechs/src/fmt/check.ts`, which the tests, the conformance harness and corpus runs call on every output they produce.

"애초에 검사에 실패한다는 건 파서/포매터 버그가 존재한다는 건데, 이건 테스트로 잡아야지 검사를 모든 포매팅에서 해야 하는 게 아님" (a failed check means a parser or formatter bug exists, which tests must catch; the check should not run on every format). A runtime self-check also cost 21.4% of format time when it existed. So the formatter has no runtime guards, fallbacks or "unsupported because the check failed" paths that hedge against its own bugs. Validation happens only at real trust boundaries: untrusted input and configuration.

## Formatters are generated from a grammar-independent DSL

Hand-writing a formatter per language is the cost this design removes: "언어별로 formatter를 새로 만드는 일은 매우 귀찮으니까, tree-sitter가 하듯이 codegen을 만드는 거야" (writing a new formatter per language is tedious, so build codegen the way tree-sitter does). Each language writes its layout per node kind in a TypeScript DSL (`packages/syntechs/src/fmt/dsl/dsl.ts`), and codegen compiles it to straight-line TypeScript against the linear stream API (`packages/syntechs/src/fmt/stream.ts`). The output, `src/grammars/<name>/fmt.gen.ts`, is generated by `packages/syntechs/generate.mjs` and not tracked in git. Generated TS is debuggable and carries no interpretation overhead.

Rejected alternatives: an overlay on `grammar.json` with layout derived automatically from it, and runtime-interpreted combinators. The DSL does not derive layout from the grammar; the grammar only types it.

### Surface

The DSL works like a token-tree builder. Arrays are sequences, strings are tokens, and named idioms replace raw group/indent/softline calls, as in the maintainer's sketch `'if': $ => ['if', grpParen($.cond), $.expr]`.

- `$.<field>` is typed from the language's grammar information. An optional field is an `Option` value with `.andThen(a => [...])`. Positional unfielded children are `$.children.at(i)`.
- Group idioms are named `grpParen`, `grpBrace` and `grpBracket`.
- `$.field.via(name)` prints a field through a named custom rule, and `tok(text).via(name)` prints a token through one (JavaScript's optional `;` is `tok(';').via('semi')`). A dedicated `semi` primitive was rejected as a JavaScript-only concept in a grammar-independent DSL, and a plain option toggle cannot express ASI hazards.
- `custom` is only for logic that genuinely needs a general-purpose language. What custom rules did is moved into grammar-independent DSL primitives wherever possible: "custom에 있던 걸 최대한 dsl internal로 표현 가능하게 만들어야 함. 최대한 특수 규칙 없어" (express as much of what customs did as possible inside the DSL, with as few special rules as possible).

### Structure and wrapping are two passes

Wrapping is a separate concern from structure: "wrapping은 TokenTreeFlattenedSeq이 만들어진 후에 도는 규칙이잖아? wrapping rule들은 별도로 처리!" (wrapping runs after the flattened sequence is built, so handle wrapping rules separately).

- Structure says what a node prints, in order. Flatten builds one token sequence for the whole document.
- Wrapping decides only flat versus broken. It runs afterwards as its own pass, keyed by node ranges, for any node kind (not only list bodies). Its list options are `packWhenAllOf`, `breakMatrix` and `itemsAsGroups`.
- `pad` and `sepBy`'s trailing separator stay in the structure as mode-conditional tokens (flat-only or broken-only).
- Comments and kept blank lines are sequence entries that flatten inserts; spec authors never write them. Wrapping reads them from the sequence, and `blankLines: "force" | "ifBroken"` decides what kept blank lines do. Custom rules receive the same entries, printed by a runtime helper, so no custom prints comments by hand.

Conceptually the passes are independent, and contributors reason about them that way. Codegen may fuse them into one pass per node as an invisible optimization only: "사용자는 두 개념을 독립적으로 알고, 독립적인 2-pass인 것과 1-pass 최적화가 내는 결과가 동등해야 해" (users know the two concepts independently, and the two-pass result must equal the one-pass optimization's). A test holds the fused code to the two-pass reference, output and anchors.

### Comment placement is its own pass

Deciding which node a comment belongs to is a pass of its own, before flatten: tree, then language-owned comment placement, then flatten, then wrapping. The default placement is a shared prettier-style attach (`packages/syntechs/src/fmt/comments.ts`); a language can supply its own (`LanguageSpec.placeComments`), as Python does with its port of ruff's placement. Overriding only a `handleComment` hook was rejected for Python: on the ruff corpus the shared attach disagreed with ruff on 33.6% of 4,409 comments and saw different neighbours for 26%, because of differences in the node model (parentheses, blocks, nested boolean operators, comprehension clauses).

## Performance and parity targets

syntechs replaces external formatters and highlighters at runtime (`docs/design/runtime.md`), so it has to prove two things against them: that its output matches, and that it is fast enough to run in a browser page. Both must be reached in TypeScript alone.

### Formatter

"we shall have parity matrix as oxfmt has before. also our goal is 5x slower than oxfmt, faster than prettier."

- **Parity** is tracked like oxc's `tasks/prettier_conformance`: a committed per-language snapshot scoring the formatter on the reference tools' own fixtures, with compatibility N/M and each failing fixture's match percentage. For JSON, CSS, JavaScript, TypeScript and TSX the fixtures are prettier's `tests/format` and the reference is oxfmt 0.70.0's output on them over prettier's defaults (the `@oxfmt` rows): "그럼 oxfmt를 정답으로 따르자. 이제 prettier 호환은 기준으로 삼지 않고." The same fixtures scored against prettier's snapshots stay in the matrix as a measurement only. Python's reference is ruff's formatter fixtures, and Kotlin's is ktfmt. The matrix lives in `packages/syntechs/conformance/README.md`.
- **Speed** is parse plus format, measured by the folder-level bench (`packages/syntechs/src/fmt/bench.node.ts`). The target is at most 5x the time of the native reference (oxfmt for JS, TS, JSON and CSS; ruff for Python) and faster than prettier. `docs/research/perf-phases.md` splits where that time goes.

### HTML highlighting backend

The planned `html` backend must match shiki per character and run at least 3x faster than warm shiki's faster engine. `docs/research/html-backend.md` records the target and its fixed constraints.

### Measured: Doc item count is not the lever

Reducing how many Doc items the printer walks does not make formatting faster; per-token work dominates. An experiment merged adjacent `TOKEN`/`TEXT` items into one run item in a post-build pass, keeping output and anchors byte-identical. It cut printer and `fits` item pops by 36-55%, yet format got slower in every language (TypeScript 550 to 625 ms, JSON 128 to 162 ms): the pass cost 15-100 ms while the printer saved at most about 5%. A build with the new printer but without the pass ran at the old speed. The printer's cost is per-token work (placement records, string building, `trimLineEnd` in `packages/syntechs/src/fmt/stream.ts`), not stepping between items. Together with the allocation measurement in `docs/research/perf-phases.md` ("Doc size and allocations", which caps allocation removal at about 10-20% of format time), this is why the formatter emits straight into the linear stream rather than building and shrinking a Doc.

A Doc-size or item-count reduction is worth trying again only if it happens at build time with no extra pass. The levers left are per-token placement records, rule dispatch during layout, the parser, and cold JIT.
